# MP-01: human update during agent investigation

- **Status:** implemented happy path; deterministic SDK/MCP checks with a simulated human update and local adapter. conditional database updates are the design baseline but remain unverified. No live model.
- **Goal:** preserve a human decision while the agent finishes investigating the same Incident.
- **Starting point:** CORE-01 findings are already saved; the agent is reasoning about its next step. One authorized human and one agent share the same tenant/Incident.

## Shared state

| Field / distinction | Meaning |
| --- | --- |
| Incident revision | Increases after each accepted update. Separate from database schema version or the local adapter's storage format |
| Selected next step | Human-selected work, owner, reason, evidence references, decision maker and time; authoritative operational direction |
| Agent proposal | A recommendation with evidence and uncertainty; accepting it does not replace the human-selected step |
| Update metadata | Trusted actor and scope, plus the revision the writer actually read; the store checks and commits atomically |

## Scenario table

| Step | Event | Expected shared state / behavior |
| --- | --- | --- |
| 1 | Agent reads revision 5 | Incident open; A1/A2, C1/C2, E1/E2/E3 and five completed calls are present. No selected next step or proposal |
| 2 | Agent reasons from revision 5 | Candidate proposal: involve Payments and inspect its errors and recent changes. Nothing is committed yet |
| 3 | Human submits an update against revision 5 | Select “Checkout owner inspects failed payment-client spans and logs”; owner Checkout team; reason “timeout location remains unknown”; cite E1/E2/E3. Commit revision 6 with author and time |
| 4 | Agent submits its candidate against revision 5 | Reject the stale write: expected 5, current 6. Do not overwrite the human decision or mark the run successfully proposed. Return a conflict and the current card |
| 5 | Agent receives revision 6 | Preserve the human step, owner, reason and attribution. Keep all observations, references and completed calls. Retain the rejected candidate in the review trace, labelled stale |
| 6 | Agent reassesses using the current card | Propose supporting the Checkout-owned inspection using the payment-timeout traces and Payments health. Explain how it supports the selected work; no telemetry refetch is needed merely because the revision changed |
| 7 | Revised proposal is submitted against revision 6 | Validate references and commit the proposal as revision 7. Preserve the human-selected step exactly; the agent proposal is a recommendation alongside it |
| 8 | Agent run ends; both actors read the Incident | Both see revision 7, the same selected human step and accepted agent proposal. Incident remains open |

## Acceptance and limits

| Check | Expected result |
| --- | --- |
| Conflict detection | Expected-revision condition and write are one atomic store operation; a separate check followed by an unguarded write is insufficient |
| No lost update | Human decision and attribution survive both the rejected and accepted agent submissions |
| No lost findings | A1/A2, C1/C2, E1/E2/E3 and completed calls remain unchanged; no duplicate source requests or references |
| No blind retry | Agent reads and reassesses the new card; it does not simply change the expected revision on its original proposal |
| Bounded completion | Only an accepted revised proposal ends this run successfully. Further conflicts remain bounded by normal turn/time limits |

- **Database design:** a tenant/Incident-scoped conditional update commits only when the stored revision matches the one read. No transaction stays open during model reasoning. All writers follow this protocol; human attribution comes from trusted application wiring.
- **Current adapter:** a stable sibling lock file protects the revision check and atomic record replacement for cooperating processes on one Unix host. This verifies local semantics, not cross-host database coordination.
- **Verification:** `uv run python -m evals.mp01`; review `output/mp-01/trace.md`. A separate test starts two writers from the same revision and checks that exactly one commits. Scripted reassessment verifies the workflow, not independent model judgment.
- **Compatibility:** database deployment needs compatible schema migrations and mixed-version rules. The local adapter accepts format 3 only. Schema/format versions and Incident revision remain separate.
- **Deferred:** database contention, uncertain commits, cross-host writers, in-flight observation races, duplicate delivery, two agents, pause/closure, real UI/chat synchronization and writer failover. No event stream or infrastructure actions are required for MP-01.
